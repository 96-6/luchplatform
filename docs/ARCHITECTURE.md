# Архитектура

Основание: ТЗ «Демоверсия образовательного модуля ЛУЧ», редакция 11.09.2026, и последовательность задач заказчика. Эта версия реализует техническую основу, аккаунты, банк контента, luch engine, анкету, входную диагностику и адаптивные индивидуальные планы с повторениями. Существующая LMS, общий вход ЛУЧ и поставщики речи/видео не предполагаются доступными без отдельного подключения.

## Компоненты

| Компонент             | Ответственность                                        | Развитие                                          |
| --------------------- | ------------------------------------------------------ | ------------------------------------------------- |
| `apps/web`            | React SPA, навигация, формы и состояния                | Кабинеты и обучение используют этот же каркас     |
| `apps/api`            | Fastify, серверная конфигурация, ошибки, доступ к базе | Доменные модули и внешние адаптеры                |
| `packages/contracts`  | Общие схемы Zod и типы API                             | Контракты пользователей, упражнений и плана       |
| `apps/api/migrations` | Версионируемая SQL-структура                           | Следующие миграции добавляют учебные сущности     |
| PostgreSQL            | Единственный источник сохранённого состояния           | Попытки, назначения, история, сессии и расписание |
| GitHub Actions        | Воспроизводимые проверки и сборка                      | Приёмочные сценарии добавляются по задачам        |

В разработке Vite перенаправляет `/api` в Fastify. На хостинге Fastify отдаёт собранный SPA и API на одном origin, за HTTPS-входом. Прямое обновление известных маршрутов возвращает SPA после серверной проверки пути, параметров, роли и ресурса; неизвестный API остаётся JSON 404. Vite использует тот же проверочный API для HTML-переходов и проксирует учебные файлы.

## База и изменения структуры

Локально PGlite исполняет PostgreSQL в Node и хранит данные на диске. Этот режим рассчитан на один API-процесс; файл блокировки предотвращает параллельное открытие. Блокировка обновляется каждые 2 секунды и признаётся устаревшей через 10 секунд без обновления. После аварийного завершения подождите 10 секунд перед повторным запуском. `pglite:memory` разрешён только в тестах.

На хостинге применяется обычный PostgreSQL с пулом `pg`, таймаутами и опциональным TLS с проверкой сертификата. Сервисный слой использует общий интерфейс запроса и транзакции. Отдельный сервер PostgreSQL проверяется в CI; использование PGlite само по себе не доказывает работу сетевого драйвера.

Миграции запускаются явно, до запуска новой версии API. Они выполняются в транзакции и записывают имя, SHA-256 и дату в `schema_migrations`. Для обычного PostgreSQL используется advisory lock. Повторный запуск пропускает применённые миграции, изменённая или неизвестная миграция блокирует обновление. Сервер не меняет структуру автоматически; readiness проверяет соответствие версии.

Добавлены технические записи, аккаунты, связи преподавателей и учебные сущности. Миграция 003 добавляет маршруты, уроки, навыки, задания, наборы и версии контентных пакетов. Блоки материалов хранятся как проверяемый JSON, связи закреплены внешними ключами. Импорт целиком транзакционный; публикация переключает текущую редакцию, сохраняя прежние. Не нужно переносить данные из браузера при развитии проекта.

Миграция 004 добавляет прохождения, шаги, черновики, попытки и учебные события. Внешние ключи связывают попытку с владельцем, шагом и закреплённой редакцией задания. Миграция 005 добавляет настройку фоновой проверки и сохраняемый контекст попытки. Пользовательские ответы остаются в базе приложения и не входят в пакеты учебного контента.

Миграция 006 добавляет текущую анкету, её редакции, диагностические сессии и результаты по навыкам. Сессия связана с владельцем, сохранённой анкетой, закреплённым набором и одним прохождением luch engine. Миграция 007 добавляет служебные операции аккаунтов. Миграция 008 добавляет планы, назначения и закреплённые тренировочные задания с внешними ключами владельца и банка. Миграция 009 добавляет состояния навыков, наблюдения, историю адаптации и дополнительные назначения; миграция 010 — роль администратора, настройки/учёт провайдеров и аудиокэш. Предыдущие миграции и данные сохраняются.

## Контракты и надёжность

- Все прикладные методы — под `/api/v1`; общий ответ `{ data, requestId }`, ошибка `{ error: { code, message, requestId, fields? } }`.
- Проверка входа выполняется на сервере. Клиент проверяет форму ответа, чтобы не отображать повреждённые данные как успешный результат.
- Тестовая запись имеет `operationId` с уникальным ограничением в базе. Повтор с тем же текстом возвращает прежнюю запись; другой текст с тем же ключом даёт 409.
- Запросы выполняются с параметрами; SQL не составляется из текста пользователя.
- luch engine получает задание из закреплённой редакции контента. Попытка, состояние шага, контекст проверки и событие `exercise.answered` сохраняются в одной транзакции. Повторная отправка не создаёт вторую попытку; обработка навыков и плана использует сохранённое событие в той же транзакции либо при завершении закрытого набора. Повторная обработка не создаёт новые наблюдения или назначения.
- API имеет request ID, ограничение размера тела, структурированные журналы и общий обработчик ошибок. Сообщения клиенту не содержат строк подключения.
- Readiness и liveness разделены: живой процесс не означает готовую базу. Недоступность базы не сбрасывает сохранённое состояние.
- Браузер ограничивает длительность ожидания, показывает ошибку и позволяет повтор. Идентификатор незавершённого сохранения сохраняется при повторе в форме.

## Доступ и интеграции следующих этапов

Реализованы серверный вход, сессии, роли и проверка связей преподавателя с учениками. Проверочный API не содержит пользовательских данных и вообще не регистрируется при `ENABLE_DEV_TOOLS=false`; production запрещает включать его. Защищённые кабинеты подключены к существующему API. Учебные материалы читаются из PostgreSQL через модуль content; служебный импорт/экспорт требует суперадмина. Сохранённые результаты доступны владельцу, его преподавателю и суперадмину. Учебные действия суперадмина от имени ученика сохраняют автора и отметку помощи.

Модули располагаются в `apps/api/src/modules`: действующие `auth`, `accounts`, `content`, `engine`, `diagnostics`, `plans`, `adaptation`, `providers`, `assistant`, `dashboard`, `speech`, `teacher`, `meetings`, `reports`. Каждый подключается к существующим настройкам, контрактам и базе. Следующие задачи добавляют миграции и маршруты, сохраняя общий запуск.

Учебные данные принадлежат этому API до подключения LMS. Если будет подключена внешняя LMS, для каждой сущности фиксируется владелец; ответы не изменяются двумя системами без правил обмена. Внешние события получают уникальный идентификатор и защиту от повторной обработки.

Помощник, STT/TTS и видео вызываются через серверные адаптеры. Секреты хранятся на сервере; клиент получает только нужный результат. OpenAI/NeuroAPI создают отдельный демонстрационный вариант, ElevenLabs озвучивает listening. Настройки и резервы платных обращений сохраняются в общей базе; суперадмин задаёт ключи и общие ограничения, администратор действует в их пределах. Сначала допускается явно обозначенный сценарный помощник. Ошибки интеграции хранятся отдельно от учебных ошибок; технический сбой не уменьшает оценку.

## Размещение и границы проверки

Dockerfile собирает сервер и клиент, финальный процесс работает от непривилегированного пользователя. Compose использует отдельный процесс миграции, readiness и постоянный том PostgreSQL. Runtime не включает локальные `.env` и базу.

Развёртывание по HTTPS, реальные поставщики, резервное копирование/восстановление, нагрузка и устройства из целевых регионов проверяются на этапе 14. Контейнерная схема готовится сейчас, но не обозначается как уже размещённая демоверсия.

## Учебный контент и luch engine

Формат импорта/экспорта описан в [CONTENT_FORMAT.md](CONTENT_FORMAT.md). Единый пакет содержит сущности и ссылки на отдельные медиафайлы. Текущий каталог и закреплённые версии читаются из базы; изменения банка не переписывают сохранённые редакции. Рубрики и задания имеют версии, авторство и права использования. Клиент получает только материал и структуру ответа.

luch engine использует `{ packageId, packageVersion, exerciseId, exerciseVersion }` для серверной проверки, сохранения исходного ответа, времени, подсказок и продолжения урока. Клиент сохраняет черновик с версией, а сервер управляет текущим шагом и повторными попытками. История не переписывается при изменении банка или новом прохождении. Устройство и соединение могут влиять на наблюдения; пометки честности требуют проверки человеком и не влияют на оценку автоматически.

Входная диагностика начинает сохранённый набор через транзакционный метод luch engine. При завершении последнего шага сервер агрегирует уже проверенные попытки по навыкам и сохраняет предварительный результат в той же транзакции. Клиент не присылает оценки; повтор завершения не создаёт второй итог. Незавершённый набор продолжает существующее прохождение со своими ответами и черновиком.

Первоначальный план сохраняется в той же транзакции, что и завершённый результат диагностики. Причины и порядок закреплены; запуск назначения использует транзакционный метод luch engine. Статусы читаются из связанных прохождений, ответы повторно не оцениваются. Явное формирование доступно для прошлых результатов без плана. События движка обновляют навыки, дополнительные назначения и историю причин. Восстановление при запуске учитывает пригодные необработанные события, пропуская незавершённые закрытые наборы. Детали — [ADAPTATION.md](ADAPTATION.md) и [PROVIDERS.md](PROVIDERS.md). Подробности — [ENGINE.md](ENGINE.md), [DIAGNOSTICS.md](DIAGNOSTICS.md) и [PLANS.md](PLANS.md).

## Помощник и аватары (задача 9)

Модуль `assistant` хранит предпочтения персонажа и пары сообщений со снимками контекста. Сервер читает закреплённые данные luch engine, а транзакция одновременно записывает реплику и отметку помощи. Преподаватель читает историю закреплённых учеников; суперадмин также видит контекст и автора. В контроле/диагностике материал и обучающие подсказки не передаются обработчику.

Миграция 011 добавляет эти сущности и persistent HeyGen jobs. Создание видео и опрос выполняются отдельным адаптером с общим бюджетом провайдеров; MP4 сохраняется в ограниченном кэше и выдаётся через авторизованный Range API. При восстановлении не повторяется оплаченный POST. Для новых дополнительных заданий модуль провайдеров выбирает непросмотренный кэш того же навыка; исчерпание возвращает техническую ошибку, сохраняя план и оценки. Подробности — [ASSISTANT.md](ASSISTANT.md).

## Голосовое взаимодействие (задача 10)

Модуль `speech` сохраняет распознавание ElevenLabs Scribe до явного подтверждения. Браузер передаёт нормализованный PCM WAV; сервер проверяет байты и длительность, резервирует общий бюджет, сохраняет `processing` и вызывает STT вне транзакции. Миграция 012 добавляет реплики, авторство, связи с попытками/чатом, отдельное подключение `elevenlabs_stt` и кэш TTS помощника. Прежние миграции и банк неизменны.

Подтверждение блокирует run и одной транзакцией вызывает `LuchEngine.answerInTransaction`, записывает обратную связь через `AssistantService.recordAnswerInTransaction` и связывает исходный/подтверждённый текст с попыткой. События и адаптация остаются в прежнем механизме; повтор не дублирует оценку или назначение. Закрытые проверки получают нейтральный ответ до завершения. Ранее полученная помощь сохраняется, технический сбой и само распознавание помощью не считаются.

TTS использует только сохранённую реплику помощника; MP3 и его привязка к сообщению сохраняются для авторизованного Range API. Повторное проигрывание обходится без провайдера. Неопределённый исход платного вызова сохраняет резерв, новый вызов требует явного повтора. Сырые записи удаляются при успешном STT/отмене/подтверждении; неудачные доступны для повтора до 24 часов и очищаются при запуске/работе голосового модуля. Подробнее — [SPEECH.md](SPEECH.md).

## Главная ученика (задача 8)

Модуль `dashboard` собирает сводку из текущей анкеты, последнего плана выбранного языка, незавершённых назначений и сохранённых попыток. Он не записывает данные при чтении и не требует миграции. Возобновление открывает существующее прохождение; запуск назначения вызывает прежний сервис плана и luch engine. Даты рекомендуемых дней учитывают часовой пояс браузера, а срок отсроченной проверки — абсолютное серверное время.

В сводку не попадают закрытые оценки незавершённой диагностики или контроля. Продолжение и последние результаты выбираются серверными запросами ко всей истории, без клиентской сборки нескольких страниц. Доступ только у текущего ученика; преподаватель и служебные роли сохраняют прежние методы просмотра. Правила и границы — [DASHBOARD.md](DASHBOARD.md).

## Проверка преподавателя (задача 11)

Модуль `teacher` добавляет ручные решения поверх сохранённой автоматической оценки. Миграция 013 сохраняет журнал действий, историю проверок, текущую ссылку на решение, редакции и отмены назначений. Ответ, рубрика, помощь и исходная оценка остаются неизменными. Чтение luch engine, главной и состояния навыков учитывает текущую оценку; производная запись наблюдения хранит также исходный результат. Проверка старого ответа пересобирает проекцию навыка, сохраняя более поздние наблюдения.

Ручные решения сериализуются с работой движка. UUID обеспечивает повтор без дубликата, редакция защищает от потерянного обновления. Явные назначения преподавателя закрепляют упражнение банка и запускаются прежним сервисом плана; история хранит причину и состояние до изменения. Отмены остаются в плане и исключаются из выполнения. Преподаватель управляет только закреплёнными учениками через эти маршруты; права отвечать за ученика не расширяются. Исходная диагностика/план остаются снимками момента создания; новые комментарии и решения показываются ученику отдельно. Подробности — [TEACHER.md](TEACHER.md).

## Расписание и открытые видеовстречи (задача 12)

Модуль `meetings` хранит расписание, участников/организаторов, сессии, чат, журнал операций, очередь управления, итог и ссылки на домашнюю работу. Миграция 014 дополняет прежние сущности. LiveKit 1.13.10 передаёт WebRTC, React-клиент загружает SDK только при открытии комнаты. API выдаёт допуск конкретному подключению, а управление выполняет серверный адаптер. Публичная сигнализация проходит через авторизованный WebSocket-шлюз приложения: каждое подключение сверяется с актуальной сессией/допуском/ограничениями. Сигнальный порт SFU закрыт от внешних клиентов; медиа передаётся WebRTC напрямую. Сохраняемые команды доставляются по порядку и повторяются после восстановления видеосервера. Реальное присутствие отмечается по списку подключений SFU, а не по выдаче допуска.

Метки активной камеры/микрофона поступают отдельным отчётом; источник проверяется по опубликованному треку, экран исключается. Списки правил раздельные. Названия и предупреждения не входят в общую информацию LiveKit и выдаются только организатору/суперадмину. Это недостоверные клиентские признаки без влияния на учебную оценку. Обычный администратор может модерировать, но не видит эти данные без роли организатора встречи.

Итог занятия и домашние назначения сохраняются одной транзакцией через выделенный транзакционный метод `TeacherService.assignInTransaction`. Назначение остаётся обычным `kind=teacher` со ссылкой встречи; запуск/проверка/адаптация не дублируются. Ученик получает только свои домашние назначения группы. Настройка, браузерные возможности и ограничения — [MEETINGS.md](MEETINGS.md).

## Прогресс и отчёт (задача 13)

Модуль `reports` читает сохранённые попытки, текущие преподавательские оценки, состояния навыков и историю планов. Сводка считает всю историю SQL-запросами, подробности используют курсоры. Общая часть данных одинакова у ученика/преподавателя, закрытые оценки незавершённых наборов не включаются в агрегаты. Каждое чтение использует согласованный снимок `REPEATABLE READ READ ONLY`; отчёт не дублирует оценивание или адаптацию.

Отдельный расчёт условного веса свидетельств использует существующие сохранённые наблюдения попыток и доступен только преподавателю ученика/суперадмину. Версия правил и вклады видны проверяющему; неизвестные/недостаточные данные не наказываются. Учебные оценки, помощь, планы и проекции навыков не изменяются. Миграция 015 добавляет индексы чтения поверх существующих сущностей. Страница `/progress` обновляется автоматически, языки и редакции контента разделены. Подробнее — [REPORTS.md](REPORTS.md).

## Интерфейсы и обслуживание после задачи 13

`navigation` применяет общий контракт страниц перед HTML и через `/navigation/access` внутри SPA. Ошибки страниц имеют действующий HTTP-статус, безопасный HTML и код обращения. Статика ограничена; учебные файлы требуют входа, опубликованной ссылки и проверки каталога. Данные по-прежнему проверяются каждым доменным API.

`operations` читает общую техническую сводку и выполняет только фиксированные разрешённые действия через существующие обработчики. Миграция 016 хранит автора, идентификатор и результат операции с уникальностью повторной доставки. Готовые события обрабатываются порциями; закрытые незавершённые наборы пропускаются. Платные обращения не повторяются, секреты не раскрываются, произвольной оболочки нет. Прежний CLI сохранён. Правила — [INTERFACES_ACCESS.md](INTERFACES_ACCESS.md).

## Оформление и локализация

Общий реестр интерфейсных языков и каталоги находятся в contracts; клиент использует `i18n`, серверные ошибки — тот же переводчик и выбор из cookie/Accept-Language. Серверный HTML самодостаточен, стили разрешены точным CSP-хешем. Миграция 017 добавляет отдельную деактивацию и причину бана; сервер проверяет статус при входе и чтении сессии. Учебные данные и прежние миграции не изменяются. Инструкции — [LOCALIZATION.md](LOCALIZATION.md).

## Почта, пароль и отдельный второй фактор

Миграция 018 добавляет защищённые хеши паролей и незавершённые входы. Обычная сессия создаётся после проверки пароля и отдельного подтверждения Authenticator; установка второго фактора также требует подтверждённую почту и пароль. Смена и сброс пароля завершают старые сессии. Миграция сохраняет пользователей, подключённые Authenticator и учебные данные; существующие аккаунты устанавливают первый пароль через письмо или суперадмина. Клиент, серверная проверка страниц и общие контракты поддерживают новые формы.

Пароли не восстанавливаются и не выдаются через API. Серверный ключ защищённых данных находится вне PostgreSQL. Суперадмин управляет аккаунтами и сбросом; остальные роли не получают хеши и инструменты управления чужими паролями. Инструкции настройки и восстановления — в README.
