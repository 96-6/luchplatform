# Обновления платформы и диагностика из LAN

Запрос от 1 ноября 2026. Проверка установленной сборки относительно GitHub main, ручная и автоматическая проверка раз в шесть часов, красная точка, установка с журналом и сохранением страницы. Состояние сервера и БД должно быть доступно обычному суперадмину с другого компьютера.

**Статус: выполнено и проверено 1 ноября 2026.** Публичное развёртывание задачи 14 не выполняется.

## Реализовано

- Вкладки суперадмина «Обновления» и «Система»; диагностический пункт `/system` доступен суперадмину независимо от `ENABLE_DEV_TOOLS`. Показатели приходят от сервера, без параметров подключения и ключей; при потере связи прежние данные помечаются устаревшими.
- Метаданные установленной сборки фиксируются при сборке. Git и экспорт исходников сопоставляются с деревом официального `96-6/luchplatform/main`; локальные правки и неизвестная/отличающаяся сборка показаны явно.
- Серверное расписание и история операций сохраняются миграцией 027. Проверка выполняется при закрытой вкладке раз в 6 часов и вручную; ошибка GitHub сохраняет последний результат. Красная точка показывает доступное обновление.
- Только суперадмин запускает установку с CSRF, авторством, аудитом и безопасным повтором одной операции. Одновременно выполняется одно обновление; репозиторий и команды не задаются браузером.
- Управляемый Node.js и отдельный агент Compose подготавливают выпуск при работающем приложении, дожидаются завершения действующих сессий встреч, останавливают API, резервируют PGlite/обычный PostgreSQL, выполняют миграции и проверяют запуск. При ошибке восстанавливаются прежние код и база. Конфигурация, пользовательские файлы и сессии сохраняются.
- Этап, журнал, время последнего сигнала и результат доступны на той же странице во время перезапуска. Новый клиент можно загрузить кнопкой после завершения. Хостинг должен поддерживать постоянные процессы Node.js либо Compose; неподключённый агент показан в интерфейсе. Инструкция — [UPDATES.md](UPDATES.md).

## Проверенные сценарии

`platform-updates.test.ts`, `build-info.test.ts`, `update-snapshot.test.ts` проверяют права и CSRF, доступ с LAN, диагностику и навигацию при отключённых dev tools, фиксированную цель и строгий ввод, авторство/аудит, повтор запроса, одновременную операцию, сохранённое расписание на 6 часов, ошибку GitHub, устаревший сигнал агента, пропуск пустых сохранённых встреч с защитой допущенных/переподключающихся и VANISH-сессий, соответствие Git/архива и сохранённой сборки, очистку секретов в журнале и восстановление настоящей файловой PostgreSQL после прерванной замены каталога.

`platform-updates.spec.ts` проверяет ручную проверку, красную точку и её сохранение после перезагрузки, стабильное имя вкладки, отключённую установку без агента, права обычного пользователя, мобильную ширину, состояние БД и восстановление диагностики после потери связи. Прежний календарный сценарий явно выбирает дату встречи: завтрашняя дата может принадлежать следующей неделе.

`scripts/test-updater.mjs` использует настоящие сборки из локальной Git-ветки main, `npm ci`, миграции, постоянную PGlite/обычный PostgreSQL и браузер. Проверены настоящий звонок LiveKit и публикация камеры через supervisor, ожидание окончания звонка при работающей прежней версии, резервирование/переключение, чтение журнала во время остановки API, недоступность журнала неавторизованному запросу, сохранение документа и сессии суперадмина. Второй выпуск меняет базу и намеренно не запускается: прежний код, содержимое базы, история миграций и действующая сессия восстанавливаются. Отдельный сценарий PostgreSQL подтверждает отсутствие частичного коммита при ошибке инструмента восстановления после закрытия stdout. Внешний ответ GitHub контролируется только в тестовых адаптерах; прикладное состояние и базы настоящие.

Локально дополнительно проверен непосредственно `npm run start:managed`: создание внешней конфигурации, миграция чистой файловой базы, запуск веб-интерфейса/API/агента и корректное завершение процессов. Экран диагностики и снимок завершённого обновления просмотрены визуально.
