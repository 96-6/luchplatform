# Обновления и состояние сервера

Суперадмин открывает **Кабинет суперадмина → Обновления**. Здесь видны установленная версия, коммит сборки, дата сборки, последняя версия `96-6/luchplatform` в `main`, время последней и следующей проверки. Сервер проверяет GitHub раз в 6 часов, даже если вкладка закрыта. Кнопка «Проверить обновления» запускает проверку сразу. При отличии сборки на вкладке появляется красная точка. Ошибка GitHub показывается отдельно и не стирает предыдущий результат.

После «Обновить систему» и подтверждения отображаются этапы, журнал, автор операции и время последнего сигнала агента. Зависимости и сборка подготавливаются при работающем приложении. Активные встречи должны завершиться до переключения. Затем агент останавливает API, сохраняет базу, применяет новые миграции и проверяет запуск. Страница продолжает читать журнал во время перезапуска; действующая сессия сохраняется. После завершения кнопка «Обновить интерфейс» загружает новый клиент в том же окне.

При ошибке до переключения приложение продолжает работать. При ошибке миграции или запуска агент восстанавливает сохранённую базу и прежний код. Если автоматическое восстановление не удалось, вкладка показывает необходимость вмешательства оператора; сохранённая копия остаётся в каталоге резервных копий. Не меняйте вручную базу, конфигурацию или исходники во время операции. Для собственного изменённого кода сначала сохраните изменения: автоматическое обновление предназначено для официальных собранных выпусков.

Агент сохраняет резервные копии трёх последних операций и используемые/последние выпуски. Копия операции с незавершённым восстановлением сохраняется до вмешательства оператора. История операций остаётся в базе.

## Обычная установка Node.js

Нужны Node.js 24, npm 11, Git, доступ к GitHub и реестру npm и право записи в каталог приложения и отдельный каталог управляемого запуска. Для отдельного PostgreSQL нужны `pg_dump`, `pg_restore`, `psql` совместимой версии (не старше сервера). Для PostgreSQL 17 используйте клиентские инструменты 17; база должна быть выделена платформе, а её пользователь должен владеть схемой `public`. Параметры подключения и существующий ключ аккаунтов сохраняются.

После обычной подготовки `.env` и первоначальной установки:

```sh
npm ci
npm run setup
npm run build
npm run start:managed
```

Перед первым управляемым запуском остановите прежний API и Vite. Команда обслуживает готовый веб-интерфейс и API вместе. В локальной конфигурации с `SERVE_WEB=false` сохраняется порт из `APP_URL` (по умолчанию 5173). При `SERVE_WEB=true` или внешнем HTTPS используется `API_PORT` (по умолчанию 3000). `API_HOST` задаёт адрес прослушивания. Отладочный вход по псевдониму для этого режима отключён; используйте обычный аккаунт и Authenticator.

По умолчанию служебные данные, новые выпуски и копии базы находятся в соседнем с исходниками каталоге `luch-runtime`. Задать постоянное место можно переменной `LUCH_RUNTIME_DIRECTORY`; оно должно находиться вне исходников и быть доступно пользователю процесса. Не удаляйте первоначальный каталог: в нём сохраняются `.env` и исходные пользовательские данные. Последующие выпуски используют те же данные и пользовательские файлы. Для VPS настройте существующий менеджер процессов на `npm run start:managed` с исходным рабочим каталогом и автоматическим перезапуском. После этого повседневные обновления выполняются из интерфейса.

Для доступа по LAN задайте в `.env` фактический адрес платформы в `APP_URL` и подходящий `API_HOST`, например `0.0.0.0`; открывайте платформу по одному и тому же адресу. При внешнем HTTPS сохраните настройку обратного прокси и `TRUST_PROXY_CIDRS`. Менять эти параметры на компьютере суперадмина не нужно.

## Docker Compose и VPS

```sh
node scripts/setup.mjs --compose
docker compose --env-file .env.compose up --build -d --wait
```

Штатный Compose подключает сервис `updater` и постоянные тома `update_state`, `update_releases` вместе с прежними `db_data` и `meeting_files`. Агент включает Git, Node.js и инструменты PostgreSQL 17. Доступ к Docker socket ему не требуется. На уже установленной старой версии один раз обновите исходники и пересоберите Compose указанной командой; следующие обновления доступны во вкладке. Сохраняйте тома и значения `.env.compose`, особенно существующие ключи и пароль БД. Повторный запуск контейнеров использует выбранный сохранённый выпуск.

При переносе сервера сохраняйте все тома, конфигурацию и исходный образ приложения. Для резервного копирования до операции настраивайте обычное внешнее резервирование сервера дополнительно к копии агента. Не используйте `down -v` для обычного обновления.

Хостинг должен разрешать постоянный процесс Node.js, сборку и сохранение выпусков либо Docker Compose. На хостинге без этих возможностей проверка версии работает, а кнопка обновления объясняет недоступность агента; установка выполняется штатными средствами хостинга. Публичное развёртывание задачи 14 здесь не выполняется.

## Диагностика с другого компьютера

**Кабинет суперадмина → Система** и пункт меню **Проверка системы** доступны обычному суперадмину независимо от `ENABLE_DEV_TOOLS`. Показатели запрашиваются у самого сервера: соединение и схема БД, задержка, время работы и память процесса, версия, агент обновлений, доступность видеосервера и настройка почты. Они обновляются каждые 15 секунд либо вручную. Секреты и адрес подключения к БД не выводятся. При потере связи последние показатели помечаются устаревшими.
